## 1. 文書の位置づけ・用語

本書は、要件定義・基本設計・詳細設計の境界をあえて薄くし、個人開発でも実装判断がぶれない粒度まで落とした統合仕様書である。

| 用語           | 定義                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 夫婦スペース   | 2人だけが共有するデータ領域。1スペースに有効なメンバーは原則2人。                                                        |
| 申請           | 片方が相手へ正式に提示する提案。                                                                                         |
| 提案バージョン | 申請内容の各版。初回申請=v1、対案=v2、再提案=v3…と追加される。過去版は上書きしない。                                     |
| 対案           | 受信側が元申請の条件を変更して返す正式な提案。チャットではない。                                                         |
| 次の対応       | 現在、正式な回答または再提案を行うべきユーザー。UI上の『誰がボールを持つか』に相当するが、ボールという表現は表示しない。 |
| 合意           | 最新の提案バージョンを相手が承認し、双方の合意内容として確定した状態。                                                   |
| 家で話す       | 却下でも承認でもない正式状態。話し合う日時を持ち、話した後に結果をアプリへ戻す。                                         |
| 監査ログ       | 誰が、いつ、何を行ったかを追記式で保存する操作履歴。                                                                     |

## 2. プロダクト概要

### 2.1 解決する問題

夫婦で話した内容が会話に埋もれ、後から確認できない。

『いつからやる』『いくらまで』『どの条件ならOK』が曖昧になる。

決めたことが未実行でも気づきにくい。

Yes/Noだけでは実際の話し合いを表現できず、条件調整がLINE等のチャットへ逃げる。

チャットでは現在のステータスや次に対応すべき人が見えにくく、重要度が下がる。

### 2.2 プロダクトの一文定義

| プロダクト定義<br>話したことを合意にし、合意したことを忘れず、条件調整の途中も『今どうなっているか／次は誰が対応するか』を明確にする、夫婦2人専用の合意・実行管理PWA。 |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 2.3 成功条件

| 指標     | 成功の定義                                                     |
| -------- | -------------------------------------------------------------- |
| 認知負荷 | ホームを開いて5秒以内に『自分が対応すべき件』が分かる。        |
| 追跡性   | 任意の合意について、初回申請から最終合意まで全提案版を追える。 |
| 対等性   | 夫・妻どちらからでも同一機能・同一制約で申請できる。           |
| 安全性   | 自分の申請を自分で承認できない。他夫婦のデータを取得できない。 |
| 実行性   | 合意後の期限・実行状況を追跡でき、期限超過を可視化できる。     |

## 4. 利用者・アカウント・ペアリング

### 4.1 アカウント原則

夫と妻は完全に別のSupabase Authユーザーとする。

アプリ内の『プロフィール切替』は禁止。相手として操作するには相手本人の認証が必要。

申請者・回答者はUI入力値ではなく auth.uid() から決定する。

role（husband/wife等）は表示用途。権限差は設けず、両者は対等。

### 4.2 ペアリング

ユーザーAが新規登録する。

ユーザーAが夫婦スペースを作成する。

サーバー側で有効期限付き招待コードを発行する。

ユーザーBが別アカウントでログインし、招待コードを入力する。

参加時に、スペースの有効メンバー数が1人であることをサーバー側で再検証する。

参加完了後は招待コードを失効させる。

| 禁止<br>招待コードだけで既存ユーザーのセッションを乗っ取れる設計にしない。招待コードは『既に認証済みの別ユーザーをスペースへ参加させる権利』として扱う。 |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 5. UX原則と情報設計

### 5.1 ホームの優先順位

| 優先 | セクション         | 意味                                        |
| ---- | ------------------ | ------------------------------------------- |
| 1    | あなたの対応が必要 | 現在 current_actor_user_id が自分。最優先。 |
| 2    | 未実行・期限超過   | 合意済みだが実行期限を過ぎている。          |
| 3    | 今日・近日の予定   | 合意済みで実施日が近い。                    |
| 4    | 相手の回答待ち     | current_actor_user_id が相手。自分は待つ。  |
| 5    | 話し合い予定       | discussion_at が設定された案件。            |
| 6    | 最近の合意         | 完了・合意内容を確認する領域。              |

### 5.2 表示原則

『誰のターン』や『ボール』はユーザー向け文言に使わない。

自分が対応する場合は『あなたの対応が必要です』。

相手が対応する場合は『妻の回答待ち』『旦那の回答待ち』等。

カード上部には状態、タイトル、金額/日時、次の対応を優先表示し、長い履歴は詳細画面へ。

色だけで状態を伝えず、アイコン＋テキストを併用する。

## 6. 業務フロー

| [新規申請]<br> \|<br> v<br>相手の回答待ち ----> 却下 ----> 終了<br> \| \|<br> \| +----> 新規/再申請は別アクション<br> \|<br> +----> 家で話す ----> 話し合い予定 ----> 結果を提案として登録<br> \|<br> +----> 条件を変えて提案 ----> 申請者の対応待ち<br> \| \|<br> \| +----> 承認 -> 合意<br> \| +----> 再提案 -> 相手の対応待ち<br> \| +----> 取下げ -> 終了<br> \|<br> +----> 承認 ----> 合意 ----> 実行待ち ----> 実行済み<br> \|<br> +----> 期限超過 |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

重要：対案はメッセージではなく、申請の正式な次バージョンである。最新バージョンだけが『現在提案されている条件』となる。

## 7. 状態機械（ステータス）

| status               | UI表示       | current_actor        | 終了状態? |
| -------------------- | ------------ | -------------------- | --------- |
| pending_response     | 回答待ち     | 相手                 | No        |
| negotiating          | 条件調整中   | 最新提案を受けた相手 | No        |
| discussion_scheduled | 話し合い予定 | 原則null / shared    | No        |
| approved             | 合意済み     | null                 | No        |
| execution_pending    | 実行待ち     | 実行担当またはnull   | No        |
| overdue              | 未実行       | 実行担当またはnull   | No        |
| completed            | 実行済み     | null                 | Yes       |
| rejected             | 却下         | null                 | Yes       |
| withdrawn            | 取下げ       | null                 | Yes       |
| cancelled            | 取消済み     | null                 | Yes       |

DB上では status と current_actor_user_id を別カラムで持つ。statusだけから『誰が次に対応するか』を推測しない。更新は単一トランザクションで行う。

## 8. 申請・対案・再提案

### 8.1 提案バージョンモデル

| Request A-102<br> v1 旦那: 4,800円で釣具を買いたい<br> v2 妻 : 2,000円までならOK<br> v3 旦那: 3,000円ならどう？<br> v4 妻 : v3を承認<br><br>最終合意: 3,000円<br>当初申請: 4,800円 |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 8.2 対案で変更可能な項目

金額、単発/月額

希望日、開始日、期限、時間

繰り返し条件

タイトル（原則は大幅変更を警告）

具体的な条件・説明

### 8.3 対案のルール

対案作成者は、現在の current_actor_user_id と一致する必要がある。

対案保存時、前バージョンは更新しない。

version_no はサーバー/DB側で採番する。

対案保存後 current_actor_user_id は相手へ移る。

対案理由は原則必須。空欄を許す場合もUIで理由入力を強く促す。

最新提案以外を直接承認できない。

古い画面から承認しようとした場合は409相当の競合として再読込させる。

### 8.4 承認の意味

承認は『最新の提案バージョン全体』への同意である。金額だけ承認、日時だけ未承認のような部分承認はMVPでは扱わない。条件を変えたい場合は対案を作る。

## 10. 通知・期限・未実行

### 10.1 通知イベント

| イベント   | 対象       | 例                       |
| ---------- | ---------- | ------------------------ |
| 新規申請   | 受信者     | 新しい申請があります     |
| 対案       | 受信者     | 条件変更の提案があります |
| 承認       | 申請関係者 | 合意が成立しました       |
| 却下       | 申請者     | 申請が却下されました     |
| 話し合い前 | 双方       | 20:00に話し合う予定です  |
| 期限前     | 関係者     | 明日が実行予定日です     |
| 期限超過   | 関係者     | まだ実行されていません   |

PWAのWeb Pushは後付け可能。iPhone/iPadではホーム画面に追加したWebアプリがユーザー操作を起点に通知許可を求める方式を採る。通知が未許可でも、アプリ内の『あなたの対応』で機能が破綻しないこと。

### 10.2 期限判定

| if agreement.completed_at is null<br>and agreement.due_at < now()<br>then display_state = "overdue" |
| --------------------------------------------------------------------------------------------------- |

statusを毎分書き換える必要はない。表示時に派生状態として判定する方法も可。ただし検索・通知ジョブで必要なら overdue_at を別途保持する。

## 13. 権限・RLS・セキュリティ

### 13.1 セキュリティ不変条件

未ログインユーザーは業務データを読めない。

ユーザーは自分が所属する夫婦スペースのデータだけ読める。

1つの有効夫婦スペースに有効メンバーは最大2人。

申請者は自分の申請を承認できない。

current_actor_user_id 以外は対案・承認・却下できない。

過去の proposal_versions はUPDATE/DELETE不可。

audit_logs は通常ユーザーからUPDATE/DELETE不可。

フロントエンドに service_role / secret key を絶対に置かない。

### 13.2 RLS基本方針

| -- 概念例<br>exists (<br> select 1<br> from couple_members cm<br> where cm.couple_id = requests.couple_id<br> and cm.user_id = auth.uid()<br> and cm.left_at is null<br>) |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

公開スキーマのテーブルはRLSを有効化する。ブラウザからはSupabase publishable keyを利用し、実際の行アクセスはJWT + RLSで制御する。

### 13.3 書き込み戦略

| 操作         | 推奨実装                    |
| ------------ | --------------------------- |
| 新規申請     | RPC create_request          |
| 対案         | RPC counter_proposal        |
| 承認         | RPC approve_latest_proposal |
| 却下         | RPC reject_request          |
| 話し合い設定 | RPC schedule_discussion     |
| 実行完了     | RPC complete_agreement      |
| 取消/変更    | 専用RPC                     |

複数テーブル更新をクライアントから順番に実行しない。途中失敗で『提案版だけ増えたがcurrent_actorが変わらない』等の不整合が起きるため。

## 15. PWA仕様

manifest.json に name / short_name / start_url / display: standalone / icons / theme_color を定義。

ホーム画面追加後はブラウザタブではなくstandalone表示を基本とする。

Service Workerはアプリシェルをキャッシュするが、承認・申請の最新データを古いキャッシュだけで確定表示しない。

オンライン必須操作（申請送信、承認、対案）はオフライン時に明確に禁止または送信待ちとして扱う。MVPは『オフライン送信キューなし』が安全。

更新時は古いJSと新しいDB仕様の混在を避けるため、更新検知UIを用意する。

| PWAの考え方<br>画面を開けることと、夫婦間で同期できることは別。オフラインでアプリシェルを表示できても、正式な申請・承認・対案はサーバー到達後にのみ成立したものとする。 |

### 24.6 予定の登録方法

#### A. 申請から予定化

| 申請: 8/30 12:00から釣りに行きたい<br> ↓<br>相手が承認<br> ↓<br>agreement 作成<br> ↓<br>calendar_event 自動生成<br> ↓<br>2人の共有カレンダーへ「合意済み」で表示 |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |

#### B. 申請中の予定

scheduled_at を持つ未合意申請は、設定によりカレンダーへ『未確定』として表示する。未確定イベントは確定予定と同じ見た目にしない。詳細を開くと『妻の回答待ち』等の次の対応を表示する。

#### C. 普通の共有予定

『共有予定として登録』を選択する。

設定が『共有予定は承認必要』なら通常の申請フローへ入る。

設定が『共有予定は直接登録可』なら作成者だけで共有カレンダーへ登録できる。

どちらの方式でも作成者・作成日時は履歴に残す。

#### D. 個人予定

本人だけに表示する予定。

相手への承認不要。

夫婦共有領域とは論理的に区別し、RLSでも本人だけに見えるようにする。

個人予定を後から共有予定へ変更する場合は、新規共有申請として扱う。

### 24.7 予定種別ごとの承認要否

| 予定種別           | 初期設定               | 備考                                 |
| ------------------ | ---------------------- | ------------------------------------ |
| 合意に由来する予定 | 必須                   | 元申請が承認されるまで確定しない。   |
| 家族予定           | 必須                   | MVP初期値。設定変更可能。            |
| 共有メモ的予定     | 任意                   | 直接登録可にしてもよい。             |
| 個人予定           | 不要                   | 本人にのみ表示。                     |
| 話し合い予定       | 設定した時点で双方表示 | 内容の合意ではなく、話す日時の共有。 |

### 24.8 繰り返し予定

例：毎週日曜20:00 家計確認、毎月1日 家計締め。

繰り返し条件は recurrence_rule で保持する。

MVPでは『毎日・毎週・毎月』＋終了日なし/終了日ありを優先する。

各回の実行状況を個別に追うため、series（定義）とoccurrence（各回）を分離する。

1回だけ変更する場合と、今後すべて変更する場合を将来区別できるデータ構造にする。

### 24.13 カレンダーと『次の対応』の連携

未確定イベントを開いた際、source_request.current_actor_user_id を参照する。

自分がcurrent_actorなら『あなたの対応が必要です』と主要CTAを表示する。

相手がcurrent_actorなら『妻の回答待ち』『旦那の回答待ち』と表示する。

合意済みイベントでは次の対応は原則なし。ただし未実行で担当者がいる場合は実行担当を表示する。

話し合いイベントは『二人で話し合う予定』として表示し、通常のcurrent_actor概念とは区別する。

### 24.14 カレンダーRLS

sharedイベントは、そのcouple_idの有効メンバー2人だけSELECT可能。

personalイベントは owner_user_id = auth.uid() のみSELECT可能。

agreement_event / deadline_event をクライアントから直接UPDATEさせず、変更申請用RPCを経由する。

personal_eventは本人のみCRUD可能。

shared_direct_eventはスペース設定と承認状態に応じてCRUDを制限する。

## 25. Version 1.2 確定事項

本章はv1.1の内容を維持しつつ、実装前に必要な判断を確定する規範的な追補である。詳細な理由と影響は `docs/decisions/` のADRを参照する。

### 25.1 Proposal / Approval

- `proposal_versions` は提案条件が変更されたときだけ増やす。承認操作では増やさない。
- 例は v1 夫 4,800円、v2 妻 2,000円、v3 夫 3,000円であり、妻がv3を承認してもv4は作らない。
- 承認イベントは `responses` に保存する。
- `agreements.proposal_version_id` は承認された最新proposal version（上記例ではv3）を参照する。
- 対案・再提案はチャットではなく正式なproposal versionであり、対案理由を必須とする。
- 最新proposalを作成した本人は、そのproposalを自己承認できない。判定基準は初回申請者ではなく `proposal_versions.proposed_by` である。

### 25.2 Request workflowとagreement execution

`requests.current_actor_user_id` を明示的に保持し、`status` だけから次の対応者を推測しない。

request workflowの永続状態は次のとおりとする。

- `pending_response`
- `negotiating`
- `discussion_scheduled`
- `approved`
- `rejected`
- `withdrawn`
- `cancelled`

agreement executionの永続状態は次のとおりとする。

- `not_required`
- `pending`
- `completed`
- `cancelled`

`execution_pending`、`completed`、`overdue` をrequest workflowへ混在させない。`overdue` は現在日時、期限、完了状態から求める派生表示であり、永続状態として保存しない。

### 25.3 家で話す

`discussion_scheduled` は「二人で話す予定」を表し、通常の次の対応者は置かない。話し合い後はどちらか一方が結果を新しいproposal versionとして登録する。登録者を `proposed_by` とし、もう一方を `requests.current_actor_user_id` とする。口頭合意だけでは `approved` にせず、相手による正式な承認を必要とする。

### 25.4 変更・取消

`requests.request_kind` は `new`、`change`、`cancellation` のいずれかとする。変更申請と取消申請では `target_agreement_id` に対象agreementを保持する。

- 変更承認: 新しいagreementを作成し、旧agreementを `superseded` とする。
- 取消承認: 対象agreementを `cancelled` とする。
- proposal、response、agreement、auditの履歴は削除しない。

### 25.5 Couple membership

- 1ユーザーが同時に所属できる有効な夫婦スペースは1つだけとする。
- 1夫婦スペースの有効ユーザーは最大2人とする。
- いずれもUIだけでなくDB制約またはtransaction内の検証で保証する。

### 25.6 Calendar projection

アプリ自身に共有カレンダーを持つ。`proposal_versions` と `agreements` が正本であり、`calendar_events` は再構築可能なprojectionである。MVPでは日時を持つ未確定proposalも `calendar_events` へ物理projectionする。proposal、agreement、projectionの更新は関連RPC内の同一transactionで行う。

`recurring_event` は独立した `event_type` にせず、繰り返しは `recurrence_series_id` で表現する。

### 25.7 日時と終日

- 時刻を持つ日時は `timestamptz` を使う。
- 終日予定は `date` を使い、00:00の `timestamptz` で代用しない。
- 基本timezoneは `Asia/Tokyo` とする。
- `calendar_events` は時刻付きイベント用の開始・終了日時と、終日用の開始・終了日を区別し、両者の整合性をCHECK制約で保証する。

### 25.8 Personal / Shared Event

personal eventは本人だけが閲覧・編集でき、相手はRLSを通じても取得できない。shared eventはMVPでは原則として相手の承認を必須とする。直接共有登録を例外として初期実装しない。

### 25.9 Audit / Realtime / Security

- 重要操作と `audit_logs` への追記は同一transactionで行う。
- 通常ユーザーによる `audit_logs` のUPDATE/DELETEは禁止する。
- Realtime通知を状態そのものとして信用せず、通知を受けたら権限付きの通常queryで再取得する。
- 操作者はclient入力ではなく `auth.uid()` から確定する。
- service role keyやsecretをfrontendへ置かない。
- 業務tableは原則RLSを有効にする。
- 複数行にまたがる重要な状態遷移はRPCで実行し、不変条件、正本、projection、監査ログを同一transactionで更新する。
